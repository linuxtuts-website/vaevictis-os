# Tests

Run on any Linux machine as root (they use network namespaces and never touch the real network).

| File | What it checks | How to run |
|---|---|---|
| `vpn_helper_logic.py` | config whitelist (hooks, SaveConfig, unknown settings, bad values, custom routing `Table`/`FwMark`, peers without `Endpoint` refused), the clean copy wg-quick reads, IPv6 handling, server names under the kill switch, interface names; (1.3) IPv6 scope IDs refused, every value of the copy in standard form, ListenPort left out, the second check on the finished copy, and 60,000 random hostile edits of real provider configs (each one refused, or accepted with a clean copy); (1.3, after Argon's review) one `[Peer]` with `AllowedIPs`, a DNS server required for a full tunnel, tunnel addresses that would take over the routing refused, a server inside the tunnel's own Address or `AllowedIPs` refused, an `Address` required, `resolvconf -x` only for a full tunnel | `python3 -I tests/vpn_helper_logic.py build/vv-vpn-helper /tmp/ks.nft` |
| `vpn_helper_flows.py` | connect / reconnect / disconnect with the real `nft`: the kill switch stays on when a reconnect fails, no DNS lookup while blocked, DNS failure takes the tunnel down, import refusals, the kill switch flag is root-only, disconnecting another tunnel keeps the kill switch; (1.3) a second tunnel refused while the kill switch guards the first one or when both would carry all traffic (a tunnel for a few networks next to the VPN allowed), "down" refused for a name that is not a tunnel (no `resolvconf -d`), the server address kept after a failed first attempt so that "connect again" works under the kill switch, the runtime copy removed when DNS cannot be set, a DNS server the routing sends outside the tunnel takes the tunnel down again, a second "up" of a tunnel that is up refused, with the kill switch on a config for a few networks refused (it would have released the kill switch) and `ks-on` for a tunnel the kill switch does not guard refused, the DNS servers of such a config not exclusive |
| `vpn_dns_route_netns.py` | (1.3) the check that every DNS server of a full tunnel is reached through the tunnel, against the kernel's real policy routing set up the way wg-quick does it: the VPN's DNS and a public DNS pass, the router of the local network, a local resolver and a "VPN DNS" inside the local network's range are refused | `unshare -n python3 -I tests/vpn_dns_route_netns.py build/vv-vpn-helper` | `unshare -n python3 -I tests/vpn_helper_flows.py build/vv-vpn-helper` |
| `vpn_killswitch_netns.sh` | packets: with the kill switch on, this PC reaches only the VPN server, virtual machines reach nothing outside the tunnel, this PC still answers its VMs | inside a Debian 13 root with `iproute2`, `nftables`, `python3`, `iputils-ping`, with `/tmp/ks-lan.nft` made by `ks_rules("proton-ch1", [("10.9.0.1", 51820)])`: `unshare -m -n` + mount `proc`, `sys`, `dev` + `chroot ROOT /tmp/kstest.sh` |
| `ssh_firewall_netns.sh` | (1.3) between two network namespaces, with the OpenSSH and nftables of a Debian 13 root: the SSH port closed while the set `ssh_open` is empty, an ed25519 key logs in, an RSA key and sftp are refused, at most 4 quick new connections from one address, the port closed again while an open session keeps working | as root: `bash tests/ssh_firewall_netns.sh DEBIAN13_ROOT` (the root needs `openssh-server`; the host needs `iproute2`, `nftables`, `openssh-client`) |
| `tcp_flags_netns.py` | (1.3) the four TCP flag rules of the firewall, packet by packet: NULL, XMAS, SYN+FIN and SYN+RST dropped (with and without ACK), 11 combinations that real connections use (among them FIN+PSH+URG+ACK) not touched | as root: `mkdir -p /tmp/fw/etc; echo 13 > /tmp/fw/etc/debian_version; VV_CHROOT=/tmp/fw VV_SKIP_CHROOT=1 build/vv-harden`, then `unshare -n python3 -I tests/tcp_flags_netns.py /tmp/fw/etc/nftables.conf` |
| `ssh_port_systemd.sh` | (1.3) the root's own systemd, booted in new namespaces: the SSH port is in the set `ssh_open` exactly while `ssh.service` runs, after boot, after restarting nftables and ssh together, after reloading or restarting nftables, while ssh restarts, after ssh stops and starts again; `ssh.service` is ordered after `nftables.service` | as root: `bash tests/ssh_port_systemd.sh DEBIAN13_ROOT` (a THROWAWAY root with `openssh-server` and `nftables`; the host needs cgroup v2) |
| `sandbox_args.sh` | which files given as arguments `vv-sandbox` makes visible and how (1.2): hidden files, `~/bin`, links (to a file, to a folder, through a linked folder) and `/tmp` read-only and alone, `/proc` and the runtime folder refused, data folders writable, secrets behind links hidden, resolved paths passed to the program. A stand-in `bwrap` prints the arguments, no sandbox is started | as root, with a user `tester`: `bash tests/sandbox_args.sh build/vv-sandbox` |
| `apps_logic.py` | the programs' own handling of crafted files (1.3): Aurora with a file declaring a huge, infinite or not-a-number duration (a crafted FLAC), VaeVictis PDF writing over a link or a link to nowhere, pages 0 wide or high, PNG export of a huge page, LinPaint+ saving over a link and refusing an image wider than the limit. The functions are taken from the real files; no window is opened | `python3 -I tests/apps_logic.py build` (needs `python3-fitz`, `python3-pil`, `python3-mutagen`) |
| `sandbox_probe.py` + `sandbox_fakebus.py` + `sandbox_probe_run.sh` + `sandbox_env.sh` | what a program can do inside `vv-sandbox` for each profile: no network, read-only system and home, data folders and the opened file's folder writable, secrets hidden, private /tmp and /run, D-Bus limited to notifications (Aurora) or the screenshot portal (LinPaint+) | in a Debian 13 root with a user `tester` (uid 1000) and an X server on :99: copy the probe to `/usr/local/lib/vaevictis/probe`, the fake bus to `/root/fakebus.py`, then `tests/sandbox_env.sh ROOT /root/sandbox_probe_run.sh` (it uses `pivot_root`: user namespaces do not work inside a chroot) |

wg-quick itself and its systemd sandbox, and the three programs on a real Wayland desktop with sound, need a real
system: see the test list in the release kit.
